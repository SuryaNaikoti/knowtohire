## 3. Security & RLS Policy Verification

### 3.1 Candidate Resume Privacy (Storage Bucket: `resumes`)
- **Vulnerability Investigated:** Can an unauthenticated visitor or competing candidate access, browse, or download private resumes uploaded by job applicants?
- **Test Procedure:** Executed anonymous HTTP GET queries directly against Supabase Storage endpoints for private buckets.
- **Result:**
  - Direct public access: **403 Forbidden** (Bucket `public: false`).
  - Storage objects require signed URLs generated by authenticated sessions with matching `user_id`.
  - Database table `candidate_profiles` has RLS enabled with policy:
    - `candidate_profiles_select_own`: `auth.uid() = user_id` (Candidates can only see their own profile).
    - `employer_select_applicant_profiles`: Employers can only view profiles for candidates who have submitted active applications to that employer's jobs.
- **Verdict:** **PASSED — Candidate resumes are completely private.**

### 3.2 Employer Application Isolation
- **Vulnerability Investigated:** Can an employer view job applications submitted to a competitor company?
- **Test Procedure:** Evaluated RLS policies on `public.job_applications`.
- **Policy In Place:**
  - `job_applications_employer_select`:
    ```sql
    EXISTS (
      SELECT 1 FROM public.jobs j 
      JOIN public.employers e ON j.employer_id = e.id 
      WHERE j.id = job_applications.job_id AND e.user_id = auth.uid()
    )
    ```
  - Anonymous query against `job_applications`: **0 records returned**.
- **Verdict:** **PASSED — Complete isolation between employer applicants.**

### 3.3 Admin Privilege Escalation Prevention
- **Vulnerability Investigated:** Can an ordinary authenticated user or candidate manipulate their profile data to gain super-admin access?
- **Test Procedure:** Inspected `public.profiles` RLS policies. Role column `role` is protected; users cannot self-update their `role` attribute to `'admin'`. Admin route guards (`src/routes/AdminRoute.tsx`) verify role on both frontend state and database auth claim.
- **Verdict:** **PASSED.**

## 4. Payment Subsystem Integrity

### 4.1 Client-Side Price Tampering Resistance
- **Test Procedure:** Simulated a client sending a modified payload to Razorpay order creation (e.g. attempting to pay ₹1 for a ₹499 item).
- **Validation:** Serverless function `api/_serverPayment.ts` rejects any order where the client-submitted amount does not match the authoritative server catalog (`authoritativePricing.ts`).
- **Cryptographic Signature Verification:** Webhook and client payment completion calls must submit `razorpay_order_id`, `razorpay_payment_id`, and `razorpay_signature`. The server recalculates:
  $$\text{HMAC-SHA256}(\text{order\_id} + "|" + \text{payment\_id}, \text{RAZORPAY\_KEY\_SECRET})$$
  and strictly verifies equality before provisioning digital access or granting subscription status.
- **Verdict:** **PASSED.**
